# Phase B — provisioning runbook

Status: local preparation only. No client exists. No cloud mutation has been executed. The next simulation requires explicit authorization for the listed account, resources, revision and budget. Never run the existing demo deployment/provisioning scripts for a client.

## Manifest and registry

Start from [the intentionally invalid template](phase-b/client-manifest.template.json). Every `REQUIRED_*` value must be replaced with an independently observed or approved value. It is not a deployable example. `ClientManifest` in `apps/admin/tools/client/manifest.ts` is the executable schema. All fields are required; unknown fields are rejected. Version 1 describes the initial **disabled** state, not an ongoing desired-state manager.

The manifest records `kind=client`, unique slug, full deployment SHA, personal Cloudflare account and Sanity organization, separate Sanity project/dataset/API version, Pages name/storefront origin, Worker name/admin origin, namespace name/ID, Studio name/app ID, personal Git repository and dedicated `client/<slug>` branch, full branding, disabled publishing bindings, private backup directory/key identifier/retention. No token, password, password hash, private hook URL, API secret or encryption key belongs in it.

Keep an explicit private JSON registry array of all OTHER clients (even `[]` for the first). Lock this registry operationally to one operator; validation is not a distributed lock. Validate before every step and re-read provider inventory to catch drift. A separate Sanity **project**, not just another dataset, is required. Names must contain the slug; shared namespaces, origins, Studio app IDs, backup destinations, key IDs and repository/branch pairs are rejected. Demo identifiers and reserved slugs are rejected. Public CDN logos must use this client's project/dataset.

A provider-generated Sanity project/Studio app ID cannot be invented to pass validation. Their creation is a separately authorized bootstrap step using the approved slug, organization and name; stop until real IDs are recorded. Namespace ID may be `null` only while planned. The first Worker deployment allocates a namespace via its new SQLite class migration. Inspect its actual ID/name/binding; do not create a second namespace or paste the demo ID. If the generated name differs, reconcile the approved manifest before proceeding. `bindObservedNamespace` supports only observed null-to-ID assignment and re-verifies every completed journal entry. Other manifest changes require a newly reviewed plan/journal, not editing a completed journal hash.

## Local commands (repository root)

Use Node 22+, Python 3, installed pnpm dependencies. `$MANIFEST`, `$REGISTRY`, `$OUTPUT` below are private absolute paths selected by the operator; `$OUTPUT` must be owned by the operator, mode 0700, outside Git. The registry excludes the manifest currently being checked.

```sh
pnpm --filter admin client-ops validate "$MANIFEST" "$REGISTRY"
pnpm --filter admin client-ops plan "$MANIFEST" "$REGISTRY"
pnpm --filter admin client-ops config "$MANIFEST" "$REGISTRY" "$OUTPUT"
pnpm --filter admin client-ops confirmation "$MANIFEST" identity
pnpm --filter admin test:client
```

`plan` returns nine ordered operations, exact targets, manifest SHA-256 and generated public config, with `mutationsExecuted: 0`. `config` exclusively creates five private JSON files (storefront, admin, Worker, Studio, Pages); existing files are not overwritten. Partial local config output may remain if a later file already exists: inspect it and use a fresh directory. `apply`, `activate`, `deploy` fail immediately. There is deliberately no live provisioning adapter.

Confirmation strings bind action, both account identities, CMS project/dataset, Pages, Worker, namespace and the full manifest digest. They are not authorization by themselves: the human must approve the concrete operation. `recoverOperation` is a dependency-injected, locally tested state machine for a future provider adapter, not a callable cloud CLI. Persist intent before requesting creation; timeout means **uncertain**, not absent. Read provider inventory, reconcile its exact identity and verify before marking complete. Never blindly retry, delete, adopt an existing resource, or treat an HTTP timeout as safe to recreate.

URLs/payloads and native commands must be rechecked against the installed tools and provider APIs immediately before authorized execution. No generic `curl` mutation wrapper or unattended batch creation is supplied. This prevents a runbook from becoming an unreviewed apply mechanism.

## Failure handling

Keep a private append-only journal with manifest hash, operation, status, timestamp, observed resource IDs, request IDs and safe error category; no credentials or private hook URLs. After uncertain creation use GET and reconcile; absence must be conclusively verified before a newly approved attempt. Preserve old journals when IDs/revision change. Do not roll back by deleting resources automatically. Initial admin remote gate and Sanity write gate remain disabled throughout failures. A successful attestation validator never enables writes.
